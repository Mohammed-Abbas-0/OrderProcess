# Distributed order processing — Phases 0-2 (infra, outbox/inbox, order saga)

Phase 0 lands central package management, a single-Postgres/four-database docker-compose, and env-overridable connection + RabbitMQ config. Phase 1 wires the MassTransit EF transactional outbox + inbox into all three bounded contexts and removes the Inventory dual-write. Phase 2 adds the dedicated `OrderProcess.Saga` host with a persisted `OrderStateMachine` driving Submitted→StockReserved→Paid→Confirmed plus a PaymentFailed→ReleaseStock→Cancelled compensation branch, the Ordering submit endpoint + status consumer, the Payment `ProcessPayment` consumer with a deterministic fail switch, and a `ReleaseStock` consumer for compensation. The solution builds clean (0 warnings / 0 errors) and the recorded evidence proves both the happy and compensation paths end-to-end against live infra.

Watch for: happy path below the fail threshold still carries a 10% random payment failure, so it is not fully deterministic (confirmed). The saga declares and correlates `StockReleased` but never handles it — compensation finalizes immediately on `PaymentFailed`, and a code comment claiming it waits for `StockReleased` is stale (confirmed). `OrderSubmitted` carries only the first order line's ProductId/Quantity, so multi-item orders reserve/release only the first product (confirmed).

**Verdict**: APPROVED

## High-level view

Central package management pins MassTransit at 8.5.11 across every project — Ordering.Api and Payment.Api are flipped down from 9.2.3, and the EF integration package is correctly referenced by its real NuGet id `MassTransit.EntityFrameworkCore` (the `...Integration` string is only the namespace). EF Core unifies at 9.0.8. The build is green.

The transactional outbox is wired on two levels: `AddEntityFrameworkOutbox + UseBusOutbox` for request-scoped publishes, and a `UseEntityFrameworkOutbox` configure-endpoints callback that applies the consumer outbox (inbox dedup + outbox publish) to every receive endpoint in all four hosts. This second level is what makes the saga correct — without it the saga's `Publish(ReserveStock)` would hit the broker before saga state committed, and the `StockReserved` reply would arrive before the instance reached `Submitted`. The Inventory dual-write is genuinely gone: every branch now publishes then does a single `SaveChangesAsync`.

The saga lives in its own host, references `Contracts` only, persists to `sagadb` through `EntityFrameworkSagaRepository` with an `xmin` optimistic-concurrency token, and finalizes instances (rows deleted on completion). The compensation branch publishes `ReleaseStock` + `CancelOrder` and finalizes. Order terminal state is applied back in Ordering by an `OrderStatusConsumer` reacting to `ConfirmOrder`/`CancelOrder` commands, keeping the `Order` aggregate inside its own context.

The deterministic fail switch (`Payment:FailAmountThreshold`, default 1000) forces failure when `Amount >= threshold`, which reliably triggers compensation. Below the threshold the domain's 90% random-success simulation remains live, so the happy path is not strictly deterministic. The `OrderStatus` enum has no `Rejected`, so the stock-reservation-failure path cancels the order — a documented, accepted simplification. `OrderSubmitted` carries only the first line item, so multi-line orders are not fully reserved.

<details>
<summary>Issues (4)</summary>

1. **Happy path not deterministic** — below the fail threshold, `Payment.Process` keeps its 90% random success, so a sub-threshold order can still land on the compensation branch ~10% of the time. For a learning demo whose point is a reproducible happy path, consider making success deterministic below the threshold (e.g. only randomize when the switch is off, or add an explicit success mode).
2. **`StockReleased` declared but never handled** — the saga correlates `StockReleasedEvent` but no `During`/`When` consumes it; `PaymentFailed` finalizes immediately after publishing `ReleaseStock`+`CancelOrder`. The inline comment says it waits for `StockReleased` before finalizing, which is false. Either observe `StockReleased` to complete cleanup, or delete the dead event/comment to avoid confusion.
3. **Multi-item orders under-reserve** — `OrderSubmitted` carries only `firstItem.ProductId/Quantity`, so an order with several lines reserves and releases stock for only the first product. Acceptable for a single-line demo but a correctness gap for real multi-line orders; document it or loop reservations per line.
4. **No `Rejected` terminal state** — `StockReservationFailed` cancels the order via the same `CancelOrder` path rather than a distinct rejected state (enum is Draft/Submitted/Confirmed/Cancelled). Documented and acceptable; flag only if the spec's "order Rejected (terminal)" wording must be honored literally.

### Central package management and the 8.5.11 pin

`Directory.Packages.props` pins `MassTransit`, `MassTransit.RabbitMQ`, and `MassTransit.EntityFrameworkCore` at 8.5.11; EF Core at 9.0.8; Npgsql at 9.0.4. Every `.csproj` under `src` carries versionless `PackageReference` entries, so Ordering.Api and Payment.Api — previously on MassTransit 9.2.3 — now resolve 8.5.11. The plan originally named the EF package `MassTransit.EntityFrameworkCoreIntegration`, which does not exist on nuget.org; the implementation corrected it to `MassTransit.EntityFrameworkCore` in the props file and all references, and the build confirms the resolve. `dotnet build OrderProcess.sln` returns 0 warnings / 0 errors and `dotnet sln list` includes `OrderProcess.Saga`.

### Two-level outbox and the saga race it closes

Each host configures `AddEntityFrameworkOutbox<TDbContext>(o => { o.UsePostgres(); o.UseBusOutbox(); })` and, critically, an endpoint callback:

```csharp
x.AddConfigureEndpointsCallback((context, name, cfg) =>
    cfg.UseEntityFrameworkOutbox<TDbContext>(context));
```

`UseBusOutbox` only replaces the publish endpoint for request/DI scopes; it does not cover consumer and saga receive endpoints. The callback adds the consumer outbox (inbox + outbox) per receive endpoint across all four hosts. This is what makes the orchestration correct: the saga's publishes are buffered until saga state commits, so the `StockReserved` reply can no longer arrive before the instance transitions to `Submitted`, and the inbox dedups by `MessageId` for at-least-once idempotency. Each DbContext (`OrderingDbContext`, `InventoryDbContext`, `PaymentDbContext`, `SagaDbContext`) registers `AddInboxStateEntity`/`AddOutboxMessageEntity`/`AddOutboxStateEntity`, and the per-context `AddOutbox` migrations plus the saga's `InitialSaga` migration create `InboxState`/`OutboxState`/`OutboxMessage` (and `OrderState` for the saga).

### Inventory dual-write removed

`ReserveStockConsumer` now follows every branch (not-found, insufficient, success) with `context.Publish(Contracts.Events.*)` then a single `repository.SaveChangesAsync()` on the consume-scoped `InventoryDbContext`. With the consumer outbox active, that one save commits the `StockItem` change and the outbox row together — the old `SaveChanges`-then-`Publish` dual-write is gone. `Contracts.Events.*` is fully qualified to avoid the `Inventory.Domain.Events.StockReserved` name clash.

### Saga state machine and compensation

`OrderStateMachine` correlates all six events by `CorrelationId` (= `OrderId`). `OrderSubmitted` stores order data and publishes `ReserveStock` → `Submitted`; `StockReserved` publishes `ProcessPayment` → `StockReserved`; `StockReservationFailed` publishes `CancelOrder` and finalizes; `PaymentCompleted` publishes `ConfirmOrder`, transitions to `Paid`, finalizes; `PaymentFailed` publishes `ReleaseStock` + `CancelOrder` and finalizes. `SetCompletedWhenFinalized()` deletes terminal instances (0 rows after completion). `OrderState` maps `RowVersion` to the Postgres `xmin` system column for optimistic concurrency, and a design-time `SagaDbContextFactory` lets `dotnet ef` run without booting MassTransit/RabbitMQ.

The compensation branch finalizes immediately after publishing `ReleaseStock`; the `StockReleasedEvent` is declared and correlated but never handled, and the comment claiming the saga waits for it before finalizing is stale. The recorded evidence shows stock is restored anyway (the `ReleaseStockConsumer` processes `ReleaseStock` independently), so this is a dead-code/comment cleanup, not a functional defect.

### Order terminal state via Ordering consumer

`OrderStatusConsumer` consumes `ConfirmOrder`/`CancelOrder` and applies `Order.Confirm()`/`Order.Cancel()` through the outbox-enlisted repository, keeping the `Order` aggregate inside Ordering (the saga references only `Contracts`). The aggregate guards are compatible with the flow: on both failure paths the order is still `Submitted`, so `Cancel()` succeeds; on success it is `Submitted`, so `Confirm()` succeeds.

### Payment fail switch

`ProcessPaymentConsumer` reads `Payment:FailAmountThreshold` (default 1000) and sets `forceFail = Amount >= threshold`, writing the `Payment` row and publishing `PaymentCompleted`/`PaymentFailed` through the outbox atomically. The switch reliably forces the compensation path. Below the threshold, `Payment.Process` retains its 90% random success from the domain model, so the happy path is not strictly reproducible.

### Isolation, endpoint removal, and comments

The saga `.csproj` references `Contracts` only — no cross-context Domain/Infrastructure leakage. The temporary `/test/publish-reserve` endpoint is gone from `Inventory.Api` (grep confirms no occurrence in source). New explanatory comments are in Arabic with English identifiers, matching the existing style.
